## What's in v0.5.0

Two doors this release, both of them about asking first — and one of them a door you can shut again. **The JSON-RPC protocol stays `1`**:
nothing existing changed shape, `initialize`'s `methods` array now names **ten**, and a client that ignores the new keys is unaffected.

### A word can match at its beginning ([#6](https://github.com/Ex-Bot-01/note-processor/issues/6))

Keyword search quotes every word of a query as an FTS5 phrase, so `grand` never reached the note that says `grandmother`. There is now a
way to ask for the beginning of a word, in three spellings of one rule:

```console
$ np search ~/vault 'grand*'          # one word marked
$ np search ~/vault --prefix grand    # every word widened
```

and over JSON-RPC, `{"method":"search","params":{"query":"grand","prefix":true}}`.

The answer says what it did. `prefix_used` and `prefix_terms` name the words that were widened, and each hit carries
`matched_exactly`: `true` when every query word appears in it as a whole word, `false` when it arrived only because a prefix reached
further, `null` when the hit came from the vector half and was never in a whole-word test at all. A query that matched nothing says so
without pretending it tried harder:

```console
nothing matched "qqzz" — not even as the start of a word
```

The default is unchanged: a query with no `*` matches whole words, exactly as it did in 0.4.0. Widening is opt-in because a vault holds
identifiers, and a search that silently prefixes them reports notes you never asked about. One character of new syntax only — a `*` at
the end of a word. A leading, doubled or mid-word star is still punctuation, and a query made of punctuation alone reports that neither
half ran rather than claiming an empty answer.

### Consent has a door: `np embeddings enable <id>` ([#7](https://github.com/Ex-Bot-01/note-processor/issues/7))

Until now the only way to turn embeddings on was to hand-edit `~/.config/note-processor/config.toml`, so an application that had asked its
user for permission had nowhere to put the answer. np now writes its own config and says what it changed:

```console
$ np embeddings enable embeddinggemma-2
wrote embeddings.provider, embeddings.model to /home/you/.config/note-processor/config.toml
embeddings on: provider = "local-model", model = "embeddinggemma-2"
nothing has been downloaded yet: the first `np embed` fetches 295.5 MB (main) and checks its digest
```

Over the pipe the same two actions are `embeddings.enable` and `embeddings.disable`, answering with the same document (`changed`,
`provider`, `model`, `fetch`, `persisted_to`). They are the only methods that refuse a parameter they cannot use: a client that sends
`"modle"` is told so rather than being told `ok`, because silently ignoring it would report consent that never happened.

What it will not do:

- **It moves no bytes.** It records consent and quotes the price — the same number `np models list --json` prints under `pinned` and the
  same one the terminal fetch prompt quotes. The download stays at `np embed`, under the announcement and digest rules it has always had.
- **It refuses rather than half-configures.** A build with no inference runtime writes nothing; a model id this build does not pin is
  refused, naming the ids it does; a config file that does not load today is left untouched, because np will not rewrite a file whose
  meaning it cannot check. Every prospective file is loaded back through np's own reader before it replaces the old one.
- **It keeps your file yours.** Comments, blank lines, unrelated keys, quoting style and line endings survive; only the two keys move.
  Enabling what is already enabled writes no bytes at all and reports `changed: []`.
- **`disable` leaves `embeddings.model` in place.** Revoking permission to download is not a licence to erase which model was chosen; the
  file stays one key away from being on again.

### Assets, and one correction to v0.4.0's page

Both assets are built by CI running the same two scripts a human runs (`.github/scripts/package-assets.sh`,
`.github/scripts/cross-build-windows.sh`), with the same portable floor as `v0.4.0`: baseline x86-64, no AVX/AVX2/AVX-512 in either half of
the binary. That floor is *measured*, not asserted — cmake's cache is read for the six per-ISA options, and the configured compiler is run
with the build's own flags over empty input to ask what it predefines, because a hosted runner's `cc` defaults above baseline x86-64 and an
option cannot withdraw what nothing asked for. The last AVX in the first candidate turned out to live in a C file that never sees cmake
(`libsqlite3-sys`, `ring`), which is why `CFLAGS`/`CXXFLAGS` and `-C target-cpu=x86-64` are part of the recipe rather than a nice touch.

There is still no Windows-MSVC or macOS asset: `crates/np-core/build.rs` refuses to build the inference runtime for those targets, and
shipping a runtime-less binary under a name that implies one would be worse than shipping nothing. `vision` is in neither archive. Neither
archive is bit-reproducible.

[`v0.4.0`'s](https://github.com/Ex-Bot-01/note-processor/releases/tag/v0.4.0) first `SHA256SUMS.txt` listed `np.exe`, which lives *inside*
the Windows zip, so the documented `sha256sum -c SHA256SUMS.txt` reported `FAILED open or read` for a file nobody could download. That page
was corrected by hand and now verifies clean; the packaging script is fixed in this release, and the publish job checks coverage both ways —
every archive is listed, and every listed name is an asset on the page.

### Windows, where five red tests were one bug — and what was behind it

`Test (windows-latest)` has failed every nightly since 2026-11-09, and until this release nobody could see why: the job died at `Docs`, on a
rustdoc lint that only Windows compiles. Behind it was a harness bug rather than five product bugs — F37 nested np's Windows data dir under
`%LOCALAPPDATA%\note-processor`, and the tests derived their assertion paths from the raw variable, one floor below where np writes. Six
dispatched CI runs removed that assumption through five call sites, and every other test file then ran on a Windows runner for the first
time: `links`, `path_keys`, `pins`, `scan`, `search_prefix`, the local-runtime suite, the fetch suite.

Two things came out of it besides greener tests. A second-writer lock case has now measured Windows write-lock behaviour once, which the
README says has never happened ("believed equivalent to Linux … and that belief is untested"). And one real finding survived, filed as
[#9](https://github.com/Ex-Bot-01/note-processor/issues/9): a name refused for holding an unpaired surrogate gets identity bytes on Windows
that carry the surrogate itself — WTF-8 (`ED A0 80`), not U+FFFD — so `path_keys::os_bytes` does have a byte spelling for a UTF-16 name,
where the card that introduced it said it had none. **Those two `walk.rs` cases are red on nightly until that is decided**, and deciding it
touches keys that live in `notes.rel_bytes`. Nothing in these archives depends on them: they are about how a refusal *report* is spelled.

### Upgrading

No config change is required, no index needs rebuilding, and the JSON-RPC protocol is unchanged. `np scan` after upgrading re-derives
nothing that was already canonical; if you were on 0.3.x, see [`v0.4.0`'s notes](https://github.com/Ex-Bot-01/note-processor/releases/tag/v0.4.0)
for the one workspace-path-key change that owed a rescan.
