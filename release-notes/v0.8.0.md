## What's in v0.8.0

A **minor** release about time rather than features: `np serve` keeps the models it has already loaded, narrows the thread
count for encoding a query, and answers `status.get` and `cancel` *while* it is working. The protocol stays **1**. Three
methods are added — `cancel`, `models.warm`, `models.release` — which is a compatible change under the rule every method in
this protocol has shipped behind: an added method cannot surprise a client that reads `initialize`'s `methods` array instead of
comparing version strings, so that array now names **thirteen** where `v0.7.0` named ten. `INDEX.md`'s bytes are unchanged, no
migration step was added (so an existing workspace database opens exactly as it is), and the CLI gained no flag: everything new
is over the pipe or in `config.toml`.

### What got faster

Measured by the change's author in WSL2 on a 16-CPU host, 55 long notes, models held — the shape of a GUI session, where one
`np serve` answers many searches:

| | `v0.7.0` | `v0.8.0` |
| --- | --- | --- |
| semantic search, idle (2nd+ request on a connection) | ~580 ms | **~50 ms** |
| semantic search, 14 busy processes on the box | 8.4–10.5 s | **0.07–0.45 s** |
| hybrid search, idle | ~700 ms | **~60 ms** |
| hybrid + `--rerank` top-5 (2048-token pairs) | 66–70 s | **34–38 s** |

Three separate causes, because they were three separate problems (**#24**, **#25**, **#26**):

* **The load is paid once per connection, not once per request.** `np serve` holds the embedder (~300 MB) and the reranker
  (~635 MB) on its worker thread. A held model is reused only while its artifact's path, size and modification time — and every
  setting that shapes the loaded context (`[embeddings] dim`, `max_tokens`, `threads`, `query_threads`) — are unchanged, and only
  after this request's digest check, so a re-fetched artifact is loaded fresh and the old one dropped. **The CLI never holds**: a
  one-shot command exits and its memory goes with it.
* **A query is not a corpus.** `[embeddings] query_threads` (`auto` = `min(threads, 2)`) narrows only the query pass: on an idle
  machine two workers encode a short query nearly as fast as twelve, and on a busy one every extra worker waits for a core — that
  cost one measured search 8× its wall time and ~35× its CPU. The answer now reports `query_threads`, so the number is readable
  rather than inferable.
* **The reranker runs at `[embeddings] threads`** instead of llama.cpp's fixed four, and a new `[search] rerank_max_tokens`
  (64–2048) bounds one scored pair. Its default is **2048**, which is the whole scoring window: every reranked order in this
  release is what `v0.7.0` produced. Lowering it trades how much of a note the ranker reads for wall time — measured on long
  notes, five pairs: 2048 → ~34 s, 1024 → ~16 s, 512 → ~7.5 s.

### What a client can see

| surface | change |
| --- | --- |
| `initialize` params | gains optional `models_idle_secs` (whole seconds; `0` keeps nothing between requests) |
| `initialize` result | gains `models_idle_secs`, and `features` gains **`rerank`** — a client that asserts an exact key list must add one name |
| `methods` array | ten → **thirteen**: `cancel`, `models.warm`, `models.release` (appended before `shutdown`) |
| **response ordering** | `status.get` and `cancel` are answered by the reader thread the moment their line arrives, so **their responses can overtake** the response to an earlier request. Match responses by `id`; nothing else changed order — every other method still answers on one worker, in arrival order |
| `status.get` result | gains `queued` and `models_held`, and **`running` stops being always-`null`**: it is now `{request?, command, since_ms}` for the request in flight, or `null` when idle. A client written against the old sentence ("always `null`") must handle an object today |
| `cancel` | `{request, state, cancelled}` where `state` is `queued`, `running` or `unknown`; the cancelled request itself faults **-32800** (the code LSP uses for the same answer) — queued ones never run at all |
| `models.warm` | `{held, embedder, reranker}` — loads ahead of the first query so a person's first search is not the one that pays. **Never downloads** |
| `models.release` | `{released}` — the ids whose memory was handed back |
| `search` document | gains `query_threads`; its `rerank` object gains `reused`, `load_ms`, `score_ms`, `threads` (`null` when no ranker was opened) |

Two doors that already existed changed behaviour in the useful direction: a fetch inside `np serve` now warms what it brought,
and an idle server drops held models after `models_idle_secs` (default **900**) so a forgotten backend does not hold ~300 MB
overnight.

### One defect narrowed, and named rather than papered over

**#18** — two processes creating the same brand-new workspace at the same moment used to hand one of them a fault. Three
statements could produce it (`journal_mode = WAL`, a migration step, the `schema_version` insert) and all three were one fact:
nothing made first creation exclusive. The fix retries the journal-mode pragma while SQLite says *someone else holds this right
now* (20 waits of 20 ms — a 400 ms ceiling) and makes the migration runner re-read and resume when a step finds work a peer
already committed, instead of making eleven migration steps idempotent.

`crates/np-core/tests/db_first_open.rs` measures it: **16 of 80 first opens faulted before the fix**, on the author's tree. It
still faults here under enough contention, and this page says so rather than leaving it to a bug report. On the machine that
built this release (16-core Linux, deliberately oversubscribed with 24 CPU hogs):

* **3 of 6 runs** of the race test still returned `sqlite: database is locked` — at rounds 30, 36 and 44 of 60, so roughly
  **3 faults in ~580 concurrent opens (~1 in 190)**, against ~1 in 5 before. Two orders of magnitude narrower on this machine,
  not eliminated.
* The remaining fault is the documented ceiling expiring: a peer whose first open takes longer than 400 ms under load leaves the
  loser reporting what it reported before. Nothing is corrupted in this path — whenever both openers succeed the test asserts one
  complete schema and exactly one `notes` table, and that assertion held every time.

**The same file also had a harness bug, and this release fixes it.** Its `scratch()` derived a directory from tag plus process
id alone — and both tests run as threads of one binary, so they share a pid, and both call `baseline_versions()`. One test's
setup deleted the directory the other was still opening, which surfaced as `unable to open database file` on a baseline read and
once as a baseline of 2 version rows against a raced 11: an assertion about *the schema*, failing for a fault that belonged to
the harness. It is now a `TempDir` per call (`tempfile::Builder` keeping the tag as a prefix), which is what every other test
file in this crate already does. Measured on this machine under deliberate oversubscription (24 CPU hogs on 16 cores, 20 runs
each way): **12 of 20 runs failed before, and no run has since failed that way** — across the ~90 post-fix runs the harness
signatures (the baseline read, the doubled schema count) never appeared again. Every remaining failure is the product fault
above, at one assertion, which is where a narrowed race should leave you: the suite now reports only real problems.

### The claim, measured rather than promised

The suite was run on this machine against `v0.8.0` at the version bump:

| measurement | result |
| --- | --- |
| workspace tests, default features | **981 passed, 0 failed** after the change below, on two independent full runs |
| `db_first_open.rs` harness isolation | 12 of 20 runs failed before the fix, 0 after, under identical load (see above) |
| `docs/dependency-licenses.md` staleness gate (`check-deps.py`) | 150 packages, 0 problems, report regenerated for the new version |
| CI on the commit this tag points at | green (push run) |
| migration steps added | **none** — an existing database opens as `v0.7.0` left it |
| CLI surface added | none: no flag, no subcommand; `np --version` → `np 0.8.0` |

**What that row does not cover, said plainly.** It is a default-features run (`fetch` only), so the model-holding and rerank
paths this release is about — the ones gated on `local-model` — were not exercised here. Hosted CI does not grade them on this
commit either: both `Feature …` rows are gated `if: github.event_name != 'push'`, so a push to `main` runs the ubuntu test row
and waits for a PR or the nightly for the C++ shapes. What does grade the shipped shape is **the release run itself** —
`.github/scripts/package-assets.sh` builds `local-model,fetch`, and the tag's job then unpacks the archive it will publish and
refuses unless that binary's own `initialize` answers `local_model: true` and `fetch: true`, which is exactly the check **F40**
was written to make. Read that row as "default features, locally", and read the release page's asset section as the place the
feature claim gets proved.

Under oversubscription the only test that fails anywhere in the workspace is `db_first_open`'s race case, and it fails on the
product fault measured above rather than on anything in its own setup; nothing else failed under any setting I ran.

### What this release does **not** claim

* **The speed table is one host, and not the machine you will run it on.** Those figures come from a native build in WSL2. The
  Linux asset is compiled at the x86-64 baseline (`NP_LLAMA_PORTABLE=1`, `-C target-cpu=x86-64`, `-march=x86-64`) so it starts on
  an old CPU, which costs SIMD width: a download will be slower than the table. No latency has been measured on a published
  asset for this release — `docs/reference-releases.md` gains that row when one is downloaded and run.
* **Nothing was measured on Windows.** The `x86_64-pc-windows-gnu-cross` asset is cross-built, inspected (import table, runtime
  imports, llama.cpp present in the bytes) and never executed — as its `ABOUT-windows-gnu-cross.md` says.
* **Held models are per connection.** Two `np serve` processes hold two copies: ~300 MB each, plus ~635 MB where a reranker is
  warm. Idle release at 900 s and `models.release` bound that; there is no shared cache between processes, and no claim that one
  exists.
* **`cancel` is cooperative between units of work** — search phases, individual rerank pairs, embed batches. A forward pass
  already in flight runs to its end, so cancelling mid-embed stops the next batch rather than the current one.
* **#18 still faults under contention**, as measured above: 14 of 30 oversubscribed runs faulted once each (rounds 1–43 of 60,
  120 concurrent opens per run), which is on the order of one fault per few hundred opens against ~1 in 5 before. The retry
  ceiling is a documented bound, and raising it trades a slower refusal report for fewer busy faults — a ruling, not an oversight.
* **No ranking-quality claim.** Retrieval is untouched; `rerank_max_tokens` defaults to the full window so orders are unchanged;
  there is still no DE/EN fixture corpus, so no measured nDCG delta exists anywhere in this repository — that remains open work
  from `v0.7.0`.

### Using it

None of the speed work needs configuring: run `np serve` and the second request on a connection is fast. A GUI that wants to be
deliberate about it sets `models_idle_secs` in its `initialize`, calls `models.warm` at window open, reads `models_held` and
`running` from `status.get` for its spinner, and sends `cancel` when a person edits their query mid-search. All of it needs the
inference runtime in the binary — build with `--features local-model`, which both shipped Linux assets are built with
(`local-model,fetch`).
