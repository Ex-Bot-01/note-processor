## What's in v0.6.0

Five findings from one reporter's pass over the published binary, each reproduced against `np-0.5.1` before anything was edited, and each
fixed on the same day it was confirmed. **The JSON-RPC protocol stays `1`, and `initialize` still answers ten methods** — nothing existing
changed shape, and a client that ignores what is new is unaffected. It is a minor release rather than a patch for one reason: **keys appear**.
A `scan` result gained two of them, and `INDEX.md`'s bytes change once for vaults holding a name with a newline or a bracket in it.

Every "before" below was measured on the `v0.5.1` asset from its release page, not read out of the source.

### A meanings-only search says which vectors are missing ([#11](https://github.com/Ex-Bot-01/note-processor/issues/11))

`"mode": "semantic"` with the artifact installed and nothing embedded:

```json
{"id":3,"jsonrpc":"2.0","result":{"fetched":null,"hits":[],"indexed":true,"keyword_used":false,"mode":"semantic","note":null,"offline":false,"prefix_terms":[],"prefix_used":false,"reason":null,"semantic_used":false,"vectors":false}}
```

That is the document np sends when it searched your notes and found nothing. `vectors: false` is the closest it came to explaining itself, and
the reference already warned that the key "is *not* the answer to 'which half ran'" — it stays `true` on a run that could not use them. So an
application had no way to tell "no matches" from "meanings were never built", and the sentence that would resolve it existed only in a doc file
the terminal does not read.

There is now a token for the state, on both doors that can produce it — `np search --mode semantic` and `"mode": "semantic"` over the pipe.
Hybrid keeps its own sentence (`reason: "no-vectors"`), because one of its halves did answer and may say so; keyword gets neither, because it
never asked:

```json
{"id":3,"jsonrpc":"2.0","result":{"fetched":null,"hits":[],"indexed":true,"keyword_used":false,"mode":"semantic","note":"no vectors in this workspace: a meanings-only search has nothing to rank and no keyword half to fall back on — `np models fetch` or `np embed` adds the semantic half","offline":false,"prefix_terms":[],"prefix_used":false,"reason":"semantic-without-vectors","semantic_used":false,"vectors":false}}
```

**A correction to the report, in fairness to whoever reads this looking for their own state.** The config it described — provider named, nothing
fetched — does *not* produce that document: a provider that is not `Ready` faults with `-32000` and names the command that would fix it, which is
the behaviour the report asked for and which this release leaves untouched. The silent empty answer needs the artifact installed *and* zero notes
embedded, which is the state right after `np models install` and before the first `np embed`. Both states are now asserted in tests.

### A tracked attachment is counted and named ([#12](https://github.com/Ex-Bot-01/note-processor/issues/12))

Five files in a vault, one of them markdown. The scan report said:

```json
{"added":5,"notes":1,"skipped":[],"unindexable":null}
```

Nothing was wrong — `.txt`, `.org` and `.rst` are attachments by design, deliberately never parsed — but the report described four files as
though they did not exist, and a support answer could only say "np indexes markdown". Now:

```json
{"added":5,"notes":1,"attachments":4,"attachment_examples":["plan.org","scratch.txt","spec.rst","summary.txt"], …}
```

The count is exact even when the five example paths do not cover it, and both keys come from one SQL predicate, so they cannot disagree with
each other or with `notes`: **`notes + attachments` is every file the workspace tracks**, asserted as an invariant. When the count is non-zero
the terminal summary says so in np's own vocabulary:

```
attachments 4 — tracked, never parsed: plan.org, scratch.txt, spec.rst, summary.txt
```

**For clients with an exact-key assertion:** add both names. Absence now means *built before 0.6.0*, which is not the same claim as zero.

### An over-long body is refused at the pin ([#13](https://github.com/Ex-Bot-01/note-processor/issues/13))

A mirror that serves 500,000,000 bytes under the file name pinned to 309,855,456 wrote all of it before refusing:

```
np: the transfer for member `main` of `embeddinggemma-2` ended after 500000000 bytes; this build pins 309855456
```

1.8 seconds of writing to a `.part` file, on a path that rewrites a shared marker every 8 MiB, ending in an error the preflight already knew.
On a nearly-full disk the failure arrives as `ENOSPC` — an I/O error where a refusal with a next command was available.

The loop now stops where the pin says to. One read buffer (1 MiB) is the most a member can overshoot by, measured on the same mirror: 4,896
bytes past the pin, 1.1 seconds, same clean refusal, `.part` and marker both gone:

```
np: the transfer for member `main` of `embeddinggemma-2` sent at least 309860352 bytes; this build pins 309855456
```

"at least", deliberately. A stream abandoned just past 310 MB did not *end* there, and the old wording would have claimed a fact the code no
longer has evidence for. Short, over-long and wrong-digest stay three separate facts with three separate next commands.

### Angle-bracket destinations resolve; code spans hold their links ([#14](https://github.com/Ex-Bot-01/note-processor/issues/14))

`[angle](<a note.md>)` is how a generator writes a link to a file whose name contains a space. np filed it as an **attachment** named
`<a note.md>`, resolved nothing, and — because attachments are not counted as unresolved notes — reported it nowhere:

| line in the note | before: kind / target | after |
| --- | --- | --- |
| `[angle](<a note.md>)` | `attachment` / `<a note.md>` | `md` / `a note.md`, resolves |
| `` `[in-code](zzz-missing.md)` `` | `md` / `zzz-missing.md`, unresolved | no row at all |
| `[plain](a note.md)` | `md` / `a note.md`, resolves | unchanged |
| `[bare](x.md extra)` | `attachment` / `x.md extra` | unchanged, now named in a test |

The bug was that the kind and the lookup were computed from two different strings; unwrapping `<…>` happens before the extension test, so both
now read the same path. Links inside backticks are no longer edges or unresolved targets — a link in code is an example, not a claim about your
vault, which is what the fenced-code rule next door already says. `unresolved_links` for that vault went from 1 to 0 with an empty
`unresolved_targets`.

Left alone on purpose: `[bare](x.md extra)` keeps its trailing word. Cutting a destination at whitespace would also cut `[t](my photo.png)` in
half, and that behaviour is documented and tested as it stands.

### A catalog entry stays on its line ([#15](https://github.com/Ex-Bot-01/note-processor/issues/15))

`INDEX.md` inserted paths and titles verbatim, so a name holding a newline stopped being one line per note, and brackets in a name broke the
link wrapped around it. Three notes on disk, scanned by `v0.5.1`, written as five physical lines:

```
- [[Bracket title]]([bracket](paren).md) · 32 B · — · →0 ←0
- [[new
line]](new
line.md) · 17 B · — · →0 ←0
- [[[Roadmap] phase (one)]](roadmap#2.md) · 30 B · — · →0 ←0
```

The same vault, same binaries' data layout, scanned by `v0.6.0` — three notes, three lines, byte sizes unchanged because only the escaping
moved:

```
- [[Bracket title]](%5Bbracket%5D%28paren%29.md) · 32 B · — · →0 ←0
- [[new\u{fffd}line]](new%0Aline.md) · 17 B · — · →0 ←0
- [[\[Roadmap\] phase (one)]](roadmap%232.md) · 30 B · — · →0 ←0
```

One helper per half, because a label is read by a person and a destination is resolved by a renderer.

Labels take backslash escapes for `[`, `]` and `\`; a control character cannot be escaped that way (a backslash before a newline is markdown's
hard break) and percent-encoding would print four characters in the text someone is reading, so it becomes U+FFFD — the same posture np takes
when it decodes bytes it cannot. Destinations are percent-escaped for `<`, `>`, `[`, `]`, `(`, `)`, `#`, `?`, `\` and every ASCII control
character. `#` and `?` join because both mean "somewhere inside the target" to every renderer: `roadmap#2.md` above was linked as `roadmap`,
which is the same class of silent mispointing as the parenthesis, and a viewer followed it to the vault root. Space stays raw, and `%` is not encoded — np does not
percent-decode destinations, so nothing can be double-encoded by an escape that exists only for readers who do decode.

**This changes published bytes.** The first scan after upgrading rewrites `INDEX.md` entries whose names hold those characters. Nothing in the
database moves: paths are the identity and always have been, and no golden file needed re-recording because none of them names a file with a
bracket, paren or newline — which is the difference between a golden check that means something and one that was overwritten.

### One red test on `main`, fixed here too

`real_model::searching_a_real_index_answers_in_both_channels` still asserted that the search document has **seven** keys; it has printed twelve
since #5 and #6. It is gated behind `NP_TEST_MODEL_PATH`, so on a machine without the weights it does not fail — it does not run, which is how a
test can stay green while describing a release that shipped two versions ago. The case now pins all twelve names and asserts
`keyword_used: true` with `semantic_used: true` — a claim only a row with real weights can make.

### Assets

Same shape as `v0.5.1`, built by CI running the same two scripts: Linux `x86_64-unknown-linux-gnu` and the Windows
`x86_64-pc-windows-gnu` cross build, each with `local-model` and `fetch` compiled in, at the portable floor — baseline x86-64, no
AVX/AVX2/AVX-512 anywhere in the binary, measured by reading cmake's cache *and* asking the configured compiler what it predefines rather than
trusting a flag. No MSVC or macOS asset exists: `build.rs` refuses to build the inference runtime for those targets, and shipping a runtime-less
file under a name implying one would be worse than shipping nothing. `vision` is in neither archive.

Verify against [`SHA256SUMS.txt`](https://github.com/Ex-Bot-01/note-processor/releases/tag/v0.6.0) on this page — it lists exactly the two
archives and nothing inside them, so `sha256sum -c SHA256SUMS.txt` is meant to pass:

```sh
sha256sum -c SHA256SUMS.txt        # Linux/macOS, run next to the archive
```

```powershell
(Get-FileHash .\np-0.6.0-x86_64-pc-windows-gnu-cross.zip).Hash.ToLower()   # Windows
```

The Linux half reproduces byte-for-byte across independent CI runs; the mingw cross-build does not, so its digest identifies *the file on this
page*.

### Upgrading from 0.5.1

Drop-in for binaries: no config change, no re-scan required, no re-embed, no protocol change, and an existing `.np/index.db` opens as it is.
Three things to know:

- **A client that asserts an exact key list over a `scan` result** must add `attachments` and `attachment_examples`. Everything else is a new
  value in an existing key (`reason`) or new text in an existing sentence (`note`).
- **`INDEX.md` changes bytes once** for vaults with a name containing a newline, bracket, paren, `#`, `?` or `<`. The scan after upgrading
  writes it; the notes themselves are untouched.
- **A Rust consumer** calling `np_core::links` sees no signature change. `ScanReport` gained two public fields, so struct-literal construction
  outside the crate needs them — which is why they are documented as derived rather than stored.
