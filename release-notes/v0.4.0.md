## What's in v0.4.0

This is a feature release, not a patch: everything below adds something a client reads, and a patch number tells someone their upgrade
cannot change what their parser sees. **The JSON-RPC protocol stays `1`** — added methods and added keys are the compatible half of it,
and `initialize`'s `methods` array is how a client finds out whether this build has them. It now names **eight**.

**A diagnostics surface you can read, with a reference for it** ([`docs/reference-diagnostics.md`](https://github.com/Ex-Bot-01/note-processor/blob/main/docs/reference-diagnostics.md)).
Levels resolve from `config.toml`, `NP_LOG` and `-v`; every refusal names the rule behind it on the diagnostic channel; `np scan`
reports why each note was skipped rather than folding them into one list; records raised inside `np serve` carry the `request` id that
caused them, and each phase (`scan`, `embed`, `search`, `fetch`) closes with `elapsed_ms`. stderr is capped and bounded: a full pipe, a
very long path or a second writer now costs a *diagnostic*, never a request, and the log file keeps its own budget when two processes
write it.

**`links.list` — the link graph became a query** (**#2**). One method answers a backlinks pane, a fix-at-source marker and a rename
pass: `edges` (who links here, with `src`, `dst`, `kind`, the `target` as its author wrote it and the 1-based `line`) and `unresolved`
(every dead target, with the note and line that wrote it — and **no `dst`**, because a path beside a dead target looks like somewhere to
click). One optional `rel` parameter means *"this note is either end of the edge"*, not "incoming"; every entry names both ends, so the
client decides which one it wanted. `indexed` separates "never scanned" from "nothing links here", which is the difference between a lint
report and an empty pane. Figure embeds are in neither list, and that gap is written down in
[`docs/design-f48-links-as-a-query.md`](https://github.com/Ex-Bot-01/note-processor/blob/main/docs/design-f48-links-as-a-query.md) rather
than left as a surprise.

**The price of a fetch, before anyone is asked to agree to one** (**#3**). `np models list --json` and `models.list` carry `pinned`: one
entry for the configured model — `{id, bytes_total, members}` — priced from the sha256-pinned table for **this build**, not from a
transport's `Content-Length`. A text-only build quotes 309,855,456 bytes; the same tree built with `vision` quotes 864,676,512. The
terminal consent prompt now quotes that same number, so the terminal and a GUI can never disagree about what someone is saying yes to.

**An answer says what ran, and whether there was anything to run against** (**#5**). Search results carry `indexed`, `keyword_used` and
`semantic_used`; a workspace nobody has ever scanned is named as such — "this workspace has never been scanned — run `np scan …`" —
instead of reporting "no matches". A GUI that showed *nothing found* for an un-indexed vault told the user their notes were empty.

**One directory is one workspace** (**#4**). `/vault` and `/vault/`, `D:\Notes` and the `D:\Notes\` a Windows folder picker hands back,
`.` and the absolute path, `a//b` and `a/b` all key one index, one model cache and one registry row now. **The upgrade cost, said
plainly**: a workspace first indexed under a spelling this release rewrites files its index under the canonical key from now on, so it
needs one `np scan`, and `np embed` to rebuild vectors. A clean spelling hashes exactly what it hashed before — pinned by digest, not
asserted.

**`status.get` answers "is this index stale?"** with a real embedding denominator instead of a note count, so "12 of 40 notes have
vectors" is a fact the client can show.

**Keyword search wants every word of the query** (**#1**) — documented where a reader meets it (README and the troubleshooting table),
because AND-of-words is what makes a narrow query narrow, and the alternative was trading a documentation problem for a
retrieval-quality one.

## The asset you download now runs on the machine you own

This is the part of the release that took thirteen CI runs, and it is a change in behaviour for anyone installing from an archive rather
than building: **`np --version` used to answer `Illegal instruction (core dumped)` on machines without AVX.**

The first CI-built Linux asset carried 14,540 AVX-512 instructions, because llama.cpp defaults to `-march=native` — it was compiled for
the CPU of the runner that built it. Turning that off was necessary and nowhere near sufficient. With every `GGML_<ISA>` option OFF, no
`-m` token in any of llama.cpp's 76 compile commands, and `-C target-cpu=x86-64` in `RUSTFLAGS`, the asset still held 46,358 wide-vector
instructions. The census named the files (`ggml-quants.c`: 6,972; `arch/x86/repack.cpp`: 6,534 — zero of each in a local build of the same
source), and one question to the compiler named the cause: **on that runner, `cc` given an empty command line predefines `__AVX__` and
`__AVX2__`.** Its default target is above the baseline, so nothing had to request AVX for the objects to be born with it, and an option
that says "do not add AVX" was describing a request nobody had made.

So the floor is now stated to everything that compiles: llama.cpp's options in `crates/np-core/build.rs`, `-march=x86-64` in
`CMAKE_C_FLAGS`/`CMAKE_CXX_FLAGS`, the same flag in `CFLAGS`/`CXXFLAGS` for the C that reaches this binary through the `cc` crate rather
than through cmake — `libsqlite3-sys` and `ring`, which is why `np --version` started working while `np scan` still died of `SIGILL`
(that one file alone: 3,793 AVX instructions with the runner's default, zero once told the floor) — and `-C target-cpu=x86-64` for Rust.
`build.rs` no longer trusts any of those flags: it runs the configured compiler over empty input and **refuses a portable build whose
predefined macros name anything above SSE2**. A developer's own build is untouched — `NP_LLAMA_PORTABLE` unset keeps llama.cpp's
`-march=native`, so building from source remains faster on modern CPUs than downloading this asset. That is now the only difference
between the two.

## How this build was graded

Local, on a machine with no AVX at all (QEMU virtual CPU, flags stop at SSE4.2): `cargo test --workspace` 887 passed / 0 failed;
`cargo fmt --all` clean; `cargo clippy --workspace --all-targets -- -D warnings` clean with default features and with
`--no-default-features`; `RUSTDOCFLAGS="--deny warnings" cargo doc --locked --workspace --no-deps` clean; the hermetic config row
(`env -u HOME -u XDG_CONFIG_HOME cargo test -p np-core --test config`) green; `.github/scripts/check-workflow-shells.sh` parses all 35
`run:` blocks — a check added this cycle, because two of these rehearsals failed on shell quoting that Actions did not look at until
minutes of cross-building had elapsed.

CI on `main` at `4483b86`: run **43522181094**, success. The release path itself was rehearsed by dispatch with `publish=false`, thirteen
times, each failure kept and fixed: **43496323581** (a broken quote in the mingw toolchain heredoc; a smoke step that priced nothing
because it configured no model), **43499590986** (two scripts writing one `SHA256SUMS.txt`, flattened onto each other by
`download-artifact --merge-multiple`; and a publish job that ran on `publish=false` because a dispatch boolean arrives as the string
`"false"`), **43501499206 / 43504458704 / 43508882452 / 43509763590** (the AVX hunt, one configuration at a time), **43511006502**,
**43511894647**, **43512813155**, **43513579928**, **43514307657** (attribution: per-file census, the compiler's predefined macros, one
verbatim compile command), **43516785288** (`np --version` runs here at last; `np scan` does not; and the Windows job fails because the
new check looked for a cache key a toolchain-file build does not write), **43522182273** (both assets green, and the one this page's notes
were written against).

**The Linux asset from 43522182273 was downloaded and run on the pre-AVX host above**, which is the only test that could have caught any
of this: `np --version` → `np 0.4.0`, exit 0; `np scan` indexed a two-note vault in 15 ms; `np serve` answered `initialize` (8 methods,
`features.local_model = true`, `features.fetch = true`), `links.list` (one edge, one unresolved target) and `models.list`
(`pinned[0] = {id: embeddinggemma-2, bytes_total: 309855456}`); `np embed` fetched the pinned artifact — 295.5 MB, digest re-checked
against `models.sha256`, `errors 0`, threads 12 of 16 — and hybrid search then returned `cos 0.9535` for a matching note and
`cos 0.8362` for a query sharing no keywords with it. Wide-vector instructions in the shipped binary: `%zmm 0`, `%ymm 4,940` — the same
count as a local build of the same tree, which is what "no AVX reached the object files" looks like from outside.

**What has not been measured.** The Windows asset has never been *executed* by anything here: it is inspected (7,090,523 bytes; imports
`ADVAPI32 KERNEL32 USERENV WS2_32 bcrypt bcryptprimitives msvcrt ntdll` and no mingw runtime DLL) and that is all the claim it carries.
Neither archive is bit-reproducible — rebuild and you get a different digest, which is why `SHA256SUMS.txt` identifies *the file you
downloaded* rather than a build. The `vision` feature is in no asset on this page. No macOS or MSVC binary exists to measure. And the
13 rehearsals above are the release path being graded, not the product: the product's grading is the CI run and the local gate list.

## Assets

| File | What it is |
| --- | --- |
| `np-0.4.0-x86_64-unknown-linux-gnu.tar.gz` | Linux x86-64, built by CI running `.github/scripts/package-assets.sh`: **inference runtime linked in** (`local-model` + `fetch`), compiled to baseline x86-64 so it starts on machines older than the runner that built it |
| `np-0.4.0-x86_64-pc-windows-gnu-cross.zip` | Windows x86-64, cross-built with mingw-w64 on Linux by `.github/scripts/cross-build-windows.sh`, runtime **in**, same baseline floor. Unsigned, **not an MSVC build**, and not bit-reproducible — its published sha256 identifies the file you downloaded; rebuilding will not reproduce it byte for byte |
| `ABOUT-windows-gnu-cross.md` | Those caveats, beside the file they describe |
| `SHA256SUMS.txt` | Both archives, joined from the per-asset checksums each build script wrote |

Every archive carries `np` (or `np.exe`), `LICENSE` and `THIRD_PARTY_NOTICES.md`. The model is never inside an archive: 309 MB arrives
only when a person runs `np setup` or `np embed`, and `NP_NO_AUTO_FETCH=1` switches that trigger off.

**`v0.3.1` also attached `run-stage5-7.ps1`; this release does not.** It is a Windows verification harness that lives outside the
repository, so nothing in CI reads it, nothing here can run it against 0.4.0, and an asset nobody grades should not appear on a page that
implies otherwise. The copy on the `v0.3.1` page remains downloadable; if it is worth shipping, it is worth committing, and then it can
come back with a build that proves it parses.

**There is no Windows-MSVC asset and no macOS asset, and that is not a minutes decision.** `crates/np-core/build.rs` compiles llama.cpp
for Linux and for `x86_64-pc-windows-gnu` with a cmake toolchain file, and refuses every other target rather than meeting a linker error —
*"no platform claim without a build measured on it"*. A runtime-less macOS or MSVC binary would arrive under a name that matches the
runtime-bearing ones, which is exactly how the last trap worked. On those platforms build from source:

```sh
cargo install --git https://github.com/Ex-Bot-01/note-processor --tag v0.4.0 -p np-cli --locked                    # index + keyword search
cargo install --git https://github.com/Ex-Bot-01/note-processor --tag v0.4.0 -p np-cli --locked --features local-model,fetch   # + inference
```

**Verify before you run it:**

```sh
sha256sum -c SHA256SUMS.txt        # Linux/macOS, next to the archive
```

```powershell
(Get-FileHash .\np-0.4.0-x86_64-pc-windows-gnu-cross.zip).Hash.ToLower()   # Windows: compare against SHA256SUMS.txt
```

If a binary from an **earlier** release refuses to start on your machine with `Illegal instruction`, that is this section's subject: it was
compiled for the CPU that built it. Rebuilding from source on your own machine has always fixed it and still does.
