## What's in v0.7.0

A **minor** release: keys appear where a client can read them, and new optional arguments are accepted. Nothing existing changed
meaning. The protocol stays **1**, `initialize` still answers the same ten methods in the same order, no method was added, `INDEX.md`'s
bytes are unchanged, and an existing workspace database opens as it is — there is no migration because there is no new column.

It ships **F51**: an optional rerank stage for `np search`. Design in `docs/design-f51-rerank-stage.md`, plan in
`docs/superpowers/plans/2026-11-21-rerank-stage.md`.

### The feature, in one paragraph

After retrieval has produced its fused list, `np search` may hand the first `rerank_top_n` **note** hits to a cross-encoder —
`bge-reranker-v2-m3`, GGUF Q8_0, 635,674,432 bytes, loaded in-process by the same pinned llama.cpp that already runs the embedding
model — and reorder those slots by the score it returns. Retrieval still decides *which* notes are candidates; the stage only decides
*their order*. It is off by default (`[search] rerank = false`), it never fetches anything itself (a search constructs no transport,
even with `[models] auto_fetch = true` — there is a test that asserts the models directory is not even created), and it works without
vectors: `--mode keyword` and `[embeddings] provider = "none"` rerank too, because the stage reads strings rather than embeddings.

    [search]
    rerank = true          # false by default
    rerank_top_n = 5       # 1..=64; nonsense is refused naming the key and the range, never clamped
    rerank_text = "title-body"   # or "body": what the model actually reads

    np search ~/Notes "wie entkalkt man eine Kaffeemühle" --rerank
    np search ~/Notes "…" --rerank --rerank-text body
    np models fetch ~/Notes --id bge-reranker-v2-m3

One cause, two policies: with `rerank = true` in the config and no artifact installed, the search answers from retrieval order, warns
on stderr and exits **0**; with `--rerank` on the command line it refuses and exits **1**, because an explicitly requested stage that
did not happen is a failed request rather than a degraded one.

### What a client can see

| surface | change |
| --- | --- |
| `search` hit keys | 12 → 15: `rerank_score`, `rerank_rank_before`, `rerank_rank_after`; all three `null` when the stage did not run, and `score` stays the retrieval number |
| `search` document | gains a top-level `rerank` object: `ran`, `reason`, `note`, `candidates`, `model`, `text` |
| `serve` `search` params | optional `rerank` (boolean or `null`) and `rerank_text`; wrong types are `-32602`, an explicitly requested but unavailable reranker is `-32000` carrying the CLI's own sentence |
| `np models list` | a separate `reranker` line, and in JSON a top-level `reranker` object (present-and-`null` in a build that pins none). The reranker gets **no** `models` row, so it cannot be selected as an embedder |
| diagnostics | four new rule tokens on the `np_core::search` target: `rerank-artifact-missing`, `rerank-runtime-not-built`, `rerank-artifact-unverified`, `rerank-cannot-score` |
| text output of an un-reranked search | byte-identical to `v0.6.1` |

### The claim, measured rather than promised

All of it on this machine (16 threads, debug build, pinned artifacts installed), and all of it reproducible:

| measurement | result |
| --- | --- |
| default workspace tests | 969 passed, 0 failed; clippy clean in both feature shapes |
| `np search` with `[search] rerank = false` | no reranker touched, no line on stderr about one — the frozen disabled document is pinned by a test |
| hybrid retrieval, no rerank | peak RSS **432 MiB** |
| keyword mode + `--rerank` (ranker alone) | peak RSS **756 MiB** |
| hybrid **+** `--rerank` (both models resident) | peak RSS **1157 MiB** — the two loads overlap for the whole run, which is the number worth improving |
| rank window 2048 tokens → 512 | peak RSS 756 → 757 MiB: KV is *not* the cost, weights actually paged in are (so this is not a lever) |
| `[embeddings] log_level = "info"` during a rank load | 141 stderr lines, 58 of them llama.cpp |
| `log_level = "off"` during a rank load | 2 stderr lines, none from the runtime — one knob now governs both loads |
| artifact verification + load | ~15 s per fresh process, announced on the human channel (`loading reranker bge-reranker-v2-m3 (verifying 635674432 bytes, once per process)`), silent under `--json` and in `np serve`, cached for a process's lifetime |
| reranker digest | sha256 `d32a877b7266f5275172458616824ce6728502416672052c2da795da3389201e` over 635,674,432 bytes, checked twice: once by the pin test against the file, once on every load |
| an embedding model asked to rerank | refused before any forward pass — rank mode also requires a classifier label (`llama_model_cls_label`), not merely RANK pooling and one output, because `n_cls_out` defaults to 1 and would otherwise accept anything |
| a reranker asked to embed | refused by name, in the other direction, for the same reason |

### What this release does **not** claim

* **No quality improvement is claimed.** nDCG@k exists in the F31 harness (`--rerank`, `--rerank-text`) and its self-test passes
  thirteen checks, but there is no DE/EN fixture corpus yet, so no measured ranking delta appears anywhere in this repository. The
  template-generated corpus that would have produced one was deleted on purpose: it would have measured the template, not retrieval.
* **`title-body` against `body` is unmeasured.** Both are selectable; neither is recommended over the other by evidence.
* **Per-pair scoring latency is unmeasured** — pairs are scored serially, so cost grows linearly in `rerank_top_n`.
* **Smaller quants are untested and unpinned.** Q5_K_M (468,390,368 bytes) and Q4_K_M (438,374,880) were measured and digested for a
  later comparison pass — the numbers are recorded in the design doc — but only Q8_0 is pinned, so nothing installs them today except
  by an explicit `--path` with a digest you supply yourself.
* **Model weights are not covered by `THIRD_PARTY_NOTICES.md`.** That file is about code compiled into the artefact you download;
  the reranker is downloaded separately, at your instruction, under its upstream terms.

### Using it

The runtime has to be in the binary: build with `--features local-model` (the Linux release asset is built
`local-model,fetch`, so it has it). Then install or fetch the artifact once per workspace, and ask for the stage per query or in config.
A binary without the feature accepts the flags and refuses honestly — `built without the local-model feature` — which is the same
posture `np embed` has taken since F38.
