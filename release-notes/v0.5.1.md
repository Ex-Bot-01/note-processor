## What's in v0.5.1

A patch: nothing a parser can see changes. No method is added, no key appears, the JSON-RPC protocol stays `1`, and `np embeddings enable` at a
terminal writes byte-identical bytes to what 0.5.0 wrote. Both fixes are things a client could not work around from outside.

### A write over `np serve` records the method that made it ([#10](https://github.com/Ex-Bot-01/note-processor/issues/10))

On 0.5.0, both doors wrote the same provenance line — and one of them was false:

```toml
# note-processor set by `np embeddings enable embeddinggemma-2` (np 0.5.0) at 2026-11-14T21:31:58Z
```

That file was created by one JSON-RPC request over stdin. No command line ran. The line is a comment in your own `config.toml`, and it is the only
durable record of who set what, so an application that shows its user an audit trail of consent would have shown them a command they never typed.

Now each door names itself. One request over stdin, and the first line of the file that answer created:

```toml
# note-processor set by the `embeddings.enable` method over `np serve` (np 0.5.1) at 2026-11-15T16:49:44Z
```

Nothing about your config needs attention on upgrade: a file an older np wrote still loads, and the terminal's spelling is unchanged.

**Breaking for Rust consumers of `np-core`, deliberately.** `config_write::set_embeddings` and `set_embeddings_in` take one more argument — the
surface performing the write — and there is no default for it. Code compiled against 0.5.0 fails at the call site with *"takes 4 arguments but 3 were
supplied"*. A default would have to mean "the terminal", which is exactly the assumption that produced the false line, and failing loudly here beats
writing a wrong record into someone's config file for years.

### Windows nightly went from red to green ([#9](https://github.com/Ex-Bot-01/note-processor/issues/9))

Two `walk.rs` cases asserted that a name refused for holding an unpaired surrogate is recorded with **lossy** identity bytes. F18 round four had made
those bytes exact (WTF-8, so `U+D800` becomes `ED A0 80`) on 2026-11-08 — three doc comments also still said the old rule — and nothing could notice,
because the assertions were `#[cfg(windows)]` while the nightly Windows job was dying earlier, at a rustdoc lint. The behaviour is now asserted as it
actually is: two refused names produce **two** identity keys with one display spelling each (`caf\u{fffd}.md`, twice), and a refused directory keeps
the surrogate in the key it is prefix-matched by, because that list decides which stored rows stay *unknown* rather than becoming `Removed`.

The refusal itself stays in force, for the reason F18 gave: display spelling, link resolution and any later re-open go through lossy text, so indexing
such a name would pair a correct key with a path that opens the wrong file. Lifting it is a separate change and needs a Windows machine in the loop.

### Assets

Same shape as `v0.5.0`, built by CI running the same two scripts: Linux `x86_64-unknown-linux-gnu` and the Windows `x86_64-pc-windows-gnu` cross
build, each with `local-model` and `fetch` compiled in, at the portable floor — baseline x86-64, no AVX/AVX2/AVX-512 anywhere in the binary, measured
by reading cmake's cache *and* asking the configured compiler what it predefines rather than trusting a flag. No MSVC or macOS asset exists: `build.rs`
refuses to build the inference runtime for those targets, and shipping a runtime-less file under a name implying one would be worse than shipping
nothing. `vision` is in neither archive.

Verify against [`SHA256SUMS.txt`](https://github.com/Ex-Bot-01/note-processor/releases/tag/v0.5.1) on this page — it lists exactly the two archives and
nothing inside them, so `sha256sum -c SHA256SUMS.txt` is meant to pass:

```sh
sha256sum -c SHA256SUMS.txt        # Linux/macOS, run next to the archive
```

```powershell
(Get-FileHash .\np-0.5.1-x86_64-pc-windows-gnu-cross.zip).Hash.ToLower()   # Windows
```

The Linux half reproduces byte-for-byte across independent CI runs; the mingw cross-build does not, so its digest identifies *the file on this page*.

### Upgrading from 0.5.0

Drop-in for binaries: no config change, no re-scan, no re-embed, no protocol change. If you compile against `np-core` as a library, add the surface
argument where you call the two functions above.
