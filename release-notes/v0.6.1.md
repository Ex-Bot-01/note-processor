## What's in v0.6.1

A **patch** release in the strict sense this repository uses: nothing a user, a client or a vault can see changes. The protocol stays
**1**, `initialize` still answers the same ten methods in the same order, no key appears or disappears, `INDEX.md`'s bytes are unchanged,
and an existing workspace database opens as it is. What changed is where the code lives and what its comments cite.

It exists because `main` carried a year's worth of internal work past `v0.6.0`, and a build you can point a colleague at is worth more than
a commit SHA.

### The claim, measured rather than promised

Both sides were run as a person would: the published `np-0.6.0-x86_64-unknown-linux-gnu.tar.gz` from `v0.6.0`'s page, and an
`np-0.6.1-x86_64-unknown-linux-gnu.tar.gz` packaged from this tree by `.github/scripts/package-assets.sh`. Two identical vaults (a wikilink,
an aliased wikilink, a markdown link, a relative link out of a subdirectory, a dead target, a task line, a `.txt` attachment, and a file
named `deep%weird [x].md`), one scratch `HOME` per side so neither reads the other's registry or database. Only the version string, each
side's own paths, and elapsed times were normalised away.

| surface | result |
| --- | --- |
| `np --version` | `np 0.6.0` → `np 0.6.1` — the only intended difference |
| `np scan <vault>` (first run) | identical report, including `attachments 1 — tracked, never parsed: notes.txt` |
| `np scan <vault>` (unchanged second run) | identical — this is the report a watcher reads |
| `INDEX.md` bytes | identical: sha256 `b91fdf537cc9dbbf9e4b23331d7f9d07c7ee77a555a7e396c7fc8603ce168c55` |
| `np search --mode keyword --json` | identical document, key for key |
| `serve` — `initialize` + `links.list` | identical: ten methods, `features {fetch:true, local_model:true, vision:false}`, `protocol 1`, same edge and same unresolved target |
| `models install --path` (309 MB artifact, digest-verified) | identical outcome lines on both sides |
| `np embed` then a hybrid query | identical document **including the cosines**: `0.7255075720287169`, `0.673628975333305`, `0.6135603431420221` |

### The one difference this found, and it is a build flag rather than a code change

The first pass at the runtime comparison did *not* match: a plain `cargo build --release` of this same tree answered
`0.7253269295809867`, `0.6734010607464608`, `0.6132950025636303` — about 2 × 10⁻⁴ below the asset, same hits in the same order. Each binary
was bit-stable across repeated runs, and the stored vectors themselves differed (`sha256` of each `embeddings.vector` prefix: `7d9680cd…`
against `444f4a6c…`), so it was not noise in the ranking step.

The variable is the instruction-set floor. `.github/scripts/package-assets.sh` builds at baseline x86-64 — `NP_LLAMA_PORTABLE=1`, which
turns every `GGML_<ISA>` off in cmake and adds `-C target-cpu=x86-64` for Rust plus `-march=x86-64` for the C that never reaches cmake
(`libsqlite3-sys`, `ring`). A default `cargo build --release` compiles llama.cpp for *this* machine's CPU instead, and different SIMD paths
accumulate the dot products in a different order. Re-packaging this tree through the script closed the gap exactly: the numbers above are
the asset's, on both sides.

Two practical consequences, since you may hit this without meaning to:

- **Comparing your own build against an asset is not a comparison of code.** Add `NP_LLAMA_PORTABLE=1` (or run the script) and the two agree
  bit for bit; that is also how you tell "the tree changed the maths" from "my CPU differs from the runner's".
- **Mixing them is untidy, not dangerous.** A vault embedded by a native build answers ordering-stable queries when read by the asset, but
  the stored vectors are different bytes. If you care about byte-identical vectors across machines, build the portable way.

### What actually moved in the source

- **`crates/np-cli/src/main.rs`: 3,234 lines → 328.** One module per command under `src/commands/` — `common`, `embed`, `embeddings`,
  `models`, `scan`, `search`, `setup` — leaving argv parsing, the `Command` enum, dispatch and `DEFAULT_SEARCH_LIMIT` in the entry point.
  `serve.rs` stayed a top-level module on purpose: it is a JSON-RPC protocol with framing and lifecycle, not a command body wearing a hat.
- **`crates/np-core/src/db.rs` → nine modules** at the seams the schema already had (`migrations`, `upgrades`, `chunks`, `notes`, `media`,
  `models`, `embeddings`, `links`, `meta`), and **`scan.rs` → five** (`write`, `found`, `publish`, `state`, `corpus`). Both files are now the
  front page of their own module: doc comments at the top, re-exports below.
- **The public API did not change.** Diffed by item name, not by eye: zero `pub` items removed and zero added in either crate, and every
  previously reachable path (`np_core::db::<name>`, `np_core::scan::<name>`) still resolves. A Rust consumer recompiles without edits.
- **Comments stopped citing the paperwork.** 1,144 comment lines carried a design-document citation — `§12 rule 6`, `F45`, `**issue #13**`,
  `(Review Focus P1)`, a dated round id — and eleven remain, each because it names something that still executes or is fixed by an outside
  standard: `docs/reference-diagnostics.md` (a documentation test asserts the token list against that manual), JSON-RPC 2.0 §5, R2/R4 of
  `.github/scripts/verify_catalog_goldens.py`, and pinned header lines such as `include/llama.h:1163-1169`. The rules they pointed at are now
  written in the code where they apply — *liveness is consent*, *origin privacy*, *no invented denominators*, *half a stamp pair is no
  check* — which is the difference between a comment that survives its own design document and one that becomes a lie.
- **Gates grew where defects were found rather than where they were easy to catch**: `#![deny(unsafe_op_in_unsafe_fn, …)]` in both crates with
  an ASan row for the FFI tests under nightly, fences for `cfg`-dead code and attribute displacement, a fence proving a comment-only commit
  really is comment-only (it caught a shifted `Serve,` argument that no compiler or test noticed), a links fence that follows relative links,
  an FFI fence comparing all eight mirrored structs instead of seven, and offline license/duplicate-major grading.
- **Tracked logs stopped naming one machine.** Probe evidence files carried `/home/agent/…` paths and one account's billing identifier;
  they now say `$HOME` and `$TMPDIR`. Every measurement in them is untouched — timestamps, timings and sha256s included.

### Assets

The same two archives as `v0.6.0`, built by the same scripts with the same features (`local-model,fetch`), at the same portable floor —
re-measured on this build rather than inherited: cmake cache `GGML_NATIVE=OFF`, `GGML_AVX=OFF`, `GGML_AVX2=OFF`, `GGML_FMA=OFF`,
`GGML_F16C=OFF`, `GGML_OPENMP=OFF`, and `.text` carrying **0 `%zmm`** references against 4,940 `%ymm` (the figure the local baseline build
has carried since 2026-11-13).

| asset | what it is |
| --- | --- |
| `np-0.6.1-x86_64-unknown-linux-gnu.tar.gz` | one `np`, runtime **in** it, baseline x86-64 |
| `np-0.6.1-x86_64-pc-windows-gnu-cross.zip` | one `np.exe`, runtime in it — cross-built with mingw-w64, **unsigned, not MSVC, not bit-reproducible** |
| macOS | *no asset exists*: needs an Apple SDK no cross-compiler here has, and `crates/np-core/build.rs` refuses to compile llama.cpp for a target it has never measured. A runtime-less macOS archive arriving under the name that matches the runtime-bearing ones is how the last trap worked. Build from source instead: `cargo install --git https://github.com/Ex-Bot-01/note-processor --tag v0.6.1 -p np-cli --locked`, add `--features local-model` if you want embeddings |

Every archive contains `np`, `LICENSE` and `THIRD_PARTY_NOTICES.md`. The model is never inside one: ~309 MB arrives only when you run
`np setup` or `np embed` (a vision projector adds ~555 MB more), and `NP_NO_AUTO_FETCH=1` switches that off.

### Upgrading from 0.6.0

Drop-in on every door: no config change, no re-scan required, no re-embed, no protocol change, and an existing workspace database opens as
it is. A client that asserts an exact key list sees nothing new to add. The only string that changes is the one `np --version` prints.
